最近补齐了三个小工具，共同点是**零运行时依赖**、单一职责、直接能用。仓库都在 GitHub 上，`npx` 就能跑。

## netpeek：局域网里到底有什么

```bash
$ netpeek scan
netpeek scanned 192.168.2.108/24 on WLAN — 254/254 addresses, 11 port(s), 7274 ms

  ADDRESS         OPEN PORTS                    DEVICE
  192.168.2.1     80/http (first open port)     TP-LINK TECHNOLOGIES 80:AE:54:8B:6A:57
  192.168.2.108   80/http (first open port)     this machine 20:79:18:8E:0A:DA

  seen in the ARP table but no probed port answered (6)
  192.168.2.102                                 randomised MAC 92:C8:FC:A3:15:AE

  2 live, 2 open port(s), 6 ARP-only entries
```

用 **TCP connect 而不是 ICMP** 做主机发现，所以不需要管理员权限，在丢弃 ping 的设备上也能用。MAC 与厂商取自操作系统的 ARP 表，不抓包、不发 ARP 请求。

[仓库](https://github.com/d20260825613-hub/netpeek)

## dropjar：把文件递给同一个网络里的任何设备

```bash
$ dropjar
dropjar serving /home/me/dropjar-inbox

  Open on any device on this network:
    http://192.168.2.108:8080/

  ttl never   max file unlimited   uploads open   delete off
  # 下面是一个二维码，手机扫一下就能打开
```

手机扫码 → 网页上传/下载，双向。不用账号、不用云、不用数据线、不用装 App。二维码是**自己写的编码器**（byte 模式、纠错等级 M、版本 1–10），因为引一个依赖会破坏零依赖的前提。

[仓库](https://github.com/d20260825613-hub/dropjar)

## tabkit：看一眼、改一改、转个格式

```bash
$ tabkit peek sales.csv
COLUMN      TYPE    FILLED  MISSING  DISTINCT  MIN   MAX    SAMPLES
region      string  7       0        3                      EU | APAC | EU
units       number  7       0        7         0     300    120 | 45 | 80
note        string  3       4        4                      needs customs form | discontinu…

$ tabkit query 'status = "open" and region in ["EU", "APAC"]' sales.csv -t csv
```

过滤用的是自己实现的表达式语言，**不碰 `eval`**。理由很直接：过滤表达式是跟着文件一起送来的数据，对数据执行 `eval` 就是远程代码执行，而这个工具的用途恰好是"看看别人发来的文件"。

[仓库](https://github.com/d20260825613-hub/tabkit)

## 为什么"零依赖"值得坚持

三个项目一共约 4000 行源码，运行时依赖数为 0。这不是洁癖，是三个具体好处：

1. **`npx` 直接跑得起来。** 没有依赖树要下载，冷启动就是下载自己。
2. **没有供应链风险。** 一个审计磁盘的小工具，不该因为某个传递依赖被投毒而拿到你的文件。
3. **十年后还能跑。** Node 的内置模块不会消失，`eslint` 的第 47 个传递依赖会。

代价是有些东西得自己写。下面这些是真正花了时间的部分。

## 自己写的东西里，哪些最容易错

### 二维码编码器：错的 QR 不会报错，它只是扫不出来

这是三个项目里最容易出错的部分。一个写坏的 QR 矩阵**仍然是一个结构完好的矩阵**，渲染出来像模像样，只是任何扫描器都读不出内容。

所以我用了三层验证，而且刻意让它们不共享假设：

1. **结构 + 数学**：把生成的矩阵拆开，检查定位图形、时序图形、固定暗模块，解出格式信息，对每个 Reed-Solomon 分块做**伴随式校验**（全零才通过），再反掩码、反交织、还原出原始文本比对。
2. **独立第三方解码器**：把矩阵渲染成像素喂给 `jsqr`（一个和本仓库毫无关系的成熟实现），10 个用例全部解出才算过。
3. **回归测试**：定位/时序/暗模块/确定性/版本选择都钉成用例。

第 1 层通过而第 2 层失败，就是这次的真实情况。抓到两个 bug：

**bug 1：时序图形整行被当成保留区。** 三个定位图形各有 8×8 的保留块，它们的并集**恰好覆盖了整条第 6 行**。于是 (6,8) 和 (8,6) 这两个本该承载数据的模块被跳过，之后按之字形顺序放置的每一个比特都错位一位。结构检查全过（定位图形和时序图形本身都是对的），`jsqr` 一个用例都解不出来。

**bug 2：格式信息的位序写反。** 15 个比特按"最低位在前"还是"最高位在前"放置，两种都能生成结构合法的矩阵。写反的后果是：罚分计算（它包含这些格子）选出不同的掩码，并且任何扫描器都读不出来。这个是靠**与参考实现逐格对比**发现的 —— 逐格比对时 441 个模块里有 23 个不同，正好是格式信息区域的格子数。

教训很实在：**校验器不能和编码器共享同一个错误假设。** 我第一版的校验器自己推导位序，于是和编码器一起错。现在它直接对照已知的 15 位码字。

### 流式 multipart 解析：边界跨 TCP 包

上传大文件不能整包读进内存。手写边界扫描的经典 bug 是**边界被切成两个 TCP 块**，于是扫描不到。表现是：小文件全对，大文件偶尔损坏。

修法是保留一个 `boundary.length + 4` 字节的滑动窗口，窗口之前的字节直接输出，尾部留着以防它是边界的前缀。验证方式是**用每一个块大小跑同一份数据**——从 1 字节到整包都跑一遍。这个要么全对，要么就是错的，所以一次字节级别的遍历就能证明。

### CSV 解析：真实文件里的四种"意外"

`split(',')` 会在这四种情况下坏掉，而这四种在真实数据里到处都是：

| 情况 | 例子 |
| --- | --- |
| 引号里含分隔符 | `"Smith, John"` |
| 引号里含换行 | `"第一行\n第二行"` |
| 引号本身被转义 | `"she said ""hi"""` |
| 文件没有结尾换行 | 最后一行 |

再加上 UTF-8 BOM（不剥掉的话第一列列名会变成 `\uFEFFid`，之后永远匹配不上）和 CRLF/LF/CR 三种换行。这些不是"可选增强"，是"能不能用"。

### 中文 Windows 的控制台是另一个平台

两个平台相关的坑：

**`arp -a` 的输出是本地化的。** 中文版 Windows 打的是 `动态`/`静态`，而不是 `dynamic`/`static`。我第一版按英文关键字过滤，结果在中文系统上**每一条都被丢掉**——所有设备都显示"unknown"，而且没有任何报错。现在解析只认行的结构（IPv4 字面量 + 六个十六进制对），与语言无关。

**半块字符会变乱码。** 用 `▀▄█` 画二维码在 UTF-8 终端里很好看，但中文 Windows 控制台默认是 GBK 代码页，画出来是一堆替换字符。现在用 `##` 和空格，高两倍但任何代码页都能显示。

## 被测试抓出来的 11 个真实 bug

按项目列一下，因为它们比"功能列表"更能说明测试值不值：

**netpeek（5 个）**

1. 本地化 Windows 的 `arp -a` 解析全军覆没（上面说过）。
2. `spawn('cmd', [])` 没有参数会启动交互式 shell 然后永久挂起——第一次真实扫描卡死。
3. 选网卡时取了**枚举顺序里的第一个**私有地址，于是 VirtualBox 的 host-only 网卡（192.168.56.1）被当成了局域网，打印出来的 URL 和二维码指向一个手机根本连不上的网络。改成按分数排序，虚拟网卡名和 host-only 网段扣分。
4. `hostsInRange` 把**子网大小**当成可用主机数报出来，导致截断提示和进度输出都是错的。
5. CLI 的取消信号读的是 `io.signal`，而测试也用这个键注入夹具——于是测试一跑，所有命令都变成"unknown option"。键名改成 `io.abortSignal`。

**dropjar（3 个）**

6. `sanitizeName` **先替换了路径分隔符再切分路径**，于是 `../../etc/passwd` 变成 `_.._etc_passwd`：看着像路径穿越的文本留下了，能识别它的分隔符被毁掉了。（文件本身安全，因为磁盘上用的是随机 id，但这个函数的意图完全反了。）
7. 被拒绝的上传**把文件留在了磁盘上**，因为清理用的是异步 `fs.rm`。对一个契约是"没通过就什么都没存"的工具，这个窗口既意外又可以避免。改成同步删除。
8. 局域网地址探测器和 netpeek 犯了同一个错（虚拟网卡优先）。

**tabkit（3 个）**

9. `--unique <列名列表>` 被完全忽略：可选参数的判断写得太宽，逗号分隔的列表没被消费掉。
10. `--quiet` 把**解析失败也吞掉了**——未闭合的引号导致整张表丢失，而消息走的是"建议性"通道。会丢数据的错误现在走一条永不被抑制的通道。
11. `fitCell` 按**字符数**而不是**显示宽度**补齐，于是中文列每行错开一列。

另外还有一批只在 CI 上暴露的问题（跨平台路径、npm 全局前缀布局、`cmd` 的引号规则），那些是另一个话题：**Windows 上跑绿完全不能说明 Linux 上没问题**，所以三个项目的 CI 都是 3 个系统 × 4 个 Node 版本的矩阵。其中最典型的一个是：bash 的 `mktemp -d` 返回 `/tmp/tmp.XXXX`，Node 把同一个字符串解析成 `D:\tmp\tmp.XXXX`——服务器一直在正常运行，只是检查脚本去了错的地方找一个文件。

## 一句话总结

写这三个工具最大的收获不是"又多了三个命令行工具"，而是**把"验证方式"当成设计的一部分**：

- 知道什么情况下自己的检查会和自己一起错（QR 的位序）；
- 知道哪些行为只有真实环境才能暴露（本地化输出、虚拟网卡、控制台代码页）；
- 知道哪些测试必须是端到端的（打包安装后跑装上 CLI，这条在 CI 上抓到了两个真实 bug）。

对个人项目来说，测试的价值不在于覆盖率数字，而在于**让你敢改**。上面第 3、4、11 条这种错，如果靠手工点一遍，是永远不会发现的。
